## Purpose

Pins the text antialiasing mode for every run that produces screenshots, so a baseline captured in one environment compares cleanly against a run in another, and reports when pinning was skipped and why.

## ADDED Requirements

### Requirement: Reporter-only runs are pinned without configuration

A run in which crvy-rprtr participates only as a reporter — the consumer invokes `playwright test` (or `vitest run`) themselves — SHALL render text with grayscale antialiasing, with no change to the consumer's Playwright or Vitest config.

The pin SHALL be established before any test worker is created, so that every worker and every browser launched from a worker inherits it.

#### Scenario: Plain playwright test in a subpixel-AA image

- **WHEN** a Linux CI job runs `npx playwright test` with the crvy-rprtr reporter configured, in an image whose fontconfig enables subpixel (LCD RGB) antialiasing
- **THEN** the screenshots the run captures are byte-identical to screenshots the same suite produces under crvy-rprtr docker run mode
- **AND** no glyph in a captured screenshot carries colored subpixel fringes

#### Scenario: Multiple parallel workers

- **WHEN** the run executes with more than one worker
- **THEN** every worker's browser renders with the pinned mode, not only the first

#### Scenario: Vitest browser-mode run

- **WHEN** a Linux run uses the Vitest reporter rather than the Playwright reporter
- **THEN** the same pin applies, on the same terms as a Playwright run

### Requirement: Pinning is opt-out, never silent when skipped

The reporter SHALL accept a `fontRendering` option with the values `grayscale` and `inherit`, defaulting to `grayscale`, matching the option both run modes already expose.

When the reporter does not pin, it SHALL emit exactly one log line naming the reason, and SHALL leave the environment untouched.

#### Scenario: Consumer opts out

- **WHEN** the reporter is configured with `fontRendering: 'inherit'`
- **THEN** no font-rendering environment variable is set
- **AND** the browser renders with the environment's own antialiasing

#### Scenario: Platform where fontconfig does not drive rendering

- **WHEN** the run is on macOS or Windows
- **THEN** the reporter does not pin, and logs that the platform's text rendering is not fontconfig-driven

#### Scenario: No system fontconfig to build on

- **WHEN** the run is on Linux but no system fontconfig root config can be found
- **THEN** the reporter does not pin, and logs that it found nothing to extend
- **AND** font lookup is left working rather than broken by a configuration with no font directories

#### Scenario: Already pinned by a crvy-rprtr run mode

- **WHEN** the reporter runs inside an environment a crvy-rprtr run mode already pinned
- **THEN** the reporter does not pin a second time, and does not log a skip reason

### Requirement: Consumer-set browser environments are detected, not overridden

A Playwright config or test that supplies its own `launchOptions.env` replaces the browser's environment wholesale, which discards an environment-based pin. The reporter SHALL detect this and SHALL NOT modify the consumer's options.

#### Scenario: Config sets launchOptions.env

- **WHEN** the resolved config or a project sets `use.launchOptions.env` and the reporter would otherwise pin
- **THEN** the reporter warns once, naming the affected project and pointing at the exported launch-option helper
- **AND** the reporter does not alter `launchOptions`

#### Scenario: Consumer applies the exported helper

- **WHEN** the config applies the exported deterministic launch-option helper
- **THEN** the run is pinned, no warning is emitted, and the screenshots match a reporter-pinned run byte for byte

### Requirement: Pinning mechanisms stay mutually byte-identical

Every mechanism crvy-rprtr offers for pinning grayscale antialiasing — the reporter's environment pin, the docker run mode's fontconfig drop-in, the local run mode's environment override, and the exported launch-option helpers — SHALL produce identical pixels for the same page, so baselines may be generated by one and verified by another.

#### Scenario: Baselines generated and verified by different mechanisms

- **WHEN** baselines are generated through one pinning mechanism and verified through another, in the same browser build
- **THEN** the comparison reports no differing pixels

#### Scenario: Non-Chromium browsers

- **WHEN** the pinned run uses Firefox or WebKit
- **THEN** the run succeeds and its screenshots are unchanged by the pin
